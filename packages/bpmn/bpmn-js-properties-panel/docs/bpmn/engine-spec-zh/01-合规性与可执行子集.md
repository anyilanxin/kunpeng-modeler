# 第 1 章 合规性与可执行子集

> 对应原规范：Ch 2 Conformance（p.31-42）

## 1.1 四种合规类型概览

BPMN 2.0 定义了四种合规类型（Conformance Type）。**工作流引擎开发者只需关注前两种**：

| 合规类型 | 中文 | 引擎是否需要 | 说明 |
| --- | --- | --- | --- |
| Process Modeling Conformance | 流程建模合规 | ❌（建模工具才需要） | 关注图形元素展示和编辑 |
| **Process Execution Conformance** | **流程执行合规** | **✅ 引擎必须** | **关注执行语义** |
| BPEL Process Execution Conformance | BPEL 执行合规 | ❌（legacy） | 映射到 WS-BPEL |
| Choreography Modeling Conformance | 编排建模合规 | ❌ | 多方 choreography |

✅ **关键结论**：开发 BPMN 引擎要遵守的是 **Process Execution Conformance**，**不是** Process Modeling Conformance。建模工具和执行引擎是两种不同的合规要求，互不强制。

> ⚠️ 注意：合规性是"全有或全无"的（all-or-nothing）。部分实现只能宣称"based on this International Standard"，不能宣称"compliant"。

## 1.2 Process Modeling 合规（建模工具才关注）

### 1.2.1 三个子类

建模合规分为三个递进子类，覆盖范围由小到大：

1. **Descriptive（描述式）**：高层建模用的可见元素，类似传统流程图
2. **Analytic（分析式）**：包含 Descriptive，加上约一半的完整建模元素
3. **Common Executable（通用可执行）**：聚焦可执行流程模型所需元素

## 1.3 Process Execution 合规（引擎核心要求）

> 对应原规范 §2.3（p.40）

### 1.3.1 执行语义要求 ✅

✅ **规范性要求**（Normative）：

- 引擎**必须完整支持和解释**操作语义（operational semantics）和活动生命周期（Activity life-cycle）
- 引擎**必须完整支持和解释**底层数据元模型
- Clause 14 中的非操作性元素（Non-operational elements）可以被忽略

ℹ️ **说明**：

- Process Execution 合规的引擎**不需要**支持 Choreography 模型
- Process Execution 合规的引擎**不需要**支持 Process Modeling 合规（图形语法）
- 引擎可以使用与规范不同的图形元素、形状、标记

### 1.3.2 流程图导入要求 ✅

✅ 引擎**必须支持** BPMN 流程图类型的导入，包括其中定义的 Collaboration（参见原表 10.1）。

## 1.4 给引擎开发者的实践建议

### 最小可执行引擎应支持的元素

基于 Common Executable 子类，**最小可用引擎（MVP）必须实现**：

```
✅ 任务：userTask, serviceTask, script（隐式）, none task
✅ 网关：exclusiveGateway, parallelGateway
✅ 事件：startEvent(None), endEvent(None), terminateEndEvent
✅ 子流程：subProcess, callActivity
✅ 数据：dataObject, ioSpecification, dataInputAssociations, dataOutputAssociations
✅ 连线：sequenceFlow（条件 + 默认）
✅ 表达式：conditionExpression（XPath）
```

**进阶能力**：

- messageIntermediateEvent（消息中间事件）→ 实现异步交互
- boundaryErrorEvent（边界错误事件）→ 实现异常处理
- multiInstanceLoopCharacteristics → 实现批处理
- timerIntermediateEvent → 实现定时任务

### 优先级建议

| 优先级 | 元素 | 引擎价值 |
| --- | --- | --- |
| P0 | Task, SequenceFlow, XOR/AND Gateway, Start/End Event | 能跑通基本流程 |
| P1 | SubProcess, CallActivity, Message Event | 支持复用和异步 |
| P1 | Boundary Error Event, Data Object, IO Specification | 支持异常和数据 |
| P2 | Timer Event, MultiInstance, Compensation | 高级流程模式 |
| P3 | Signal Event, Inclusive Gateway, Event-Based Gateway | 复杂事件路由 |
| P4 | Choreography, Transaction, AdHoc SubProcess | 极少用 |

### 规范的"灰色地带"

ℹ️ 规范允许的灵活性：

- ✅ 没有强制规定 BPMN 元素必须用什么编程语言实现
- ✅ 没有强制持久化格式（不一定要 XML/XSD，可以自己设计存储）
- ✅ 没有强制 API 形式（不一定要 REST/SOAP）
- ✅ Activity life-cycle 的内部表示可以自由设计，只要对外行为符合规范

**结论**：合规性关注的是**对外可见的行为**，不限制内部实现。这给引擎设计留出了很大空间。
