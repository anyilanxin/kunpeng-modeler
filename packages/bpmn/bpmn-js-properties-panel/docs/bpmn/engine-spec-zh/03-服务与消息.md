# 第 3 章 服务与消息

> 对应原规范：Ch 8.4.10 ItemDefinition（p.119）、8.4.11 Message（p.121）、8.4.2 Correlation（p.102-108）、8.5 Services（p.131-134）、8.4.3 Error（p.109）、8.4.4 Escalation（p.110）

## 3.1 ItemDefinition（数据类型定义）

> 对应原书 §8.4.10（p.119）

`ItemDefinition` 用于定义 BPMN 中**所有数据载体的结构**（DataObject、Message、Property、Variable 等）。

### 3.1.1 属性

| 属性 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| itemKind | `Information` \| `Physical` | Information | 标识是信息项还是物理项（引擎一般只处理 Information） |
| structureRef | Element [0..1] | — | **具体数据结构引用**（如 XSD Complex Type） |
| import | Import [0..1] | — | 数据结构所在的导入位置 |
| isCollection | boolean | false | 是否集合类型 |

### 3.1.2 引擎实现要点

✅ **规范性要求**：

- `Definitions.typeLanguage` 默认为 XML Schema（`http://www.w3.org/2001/XMLSchema`）
- Common Executable 子类**强制**使用 XML Schema 作为类型定义语言
- 结构定义是**独立实体**，必须通过引用使用，不能内联

ℹ️ **实践建议**：

- 引擎内部可以将 `structureRef` 解析为运行时类型（Java Class、JSON Schema 等）
- `isCollection=true` 时，类型本身必须是集合类型，否则模型非法
- 引擎可以**放宽**类型限制，允许动态类型（如 JSON Map），但需要在文档中声明

## 3.2 Message（消息）

> 对应原书 §8.4.11（p.121）

`Message` 表示**两个 Participant 之间通信的内容**。

### 3.2.1 属性

| 属性    | 类型                  | 说明                         |
| ------- | --------------------- | ---------------------------- |
| name    | string                | 消息名称                     |
| itemRef | ItemDefinition [0..1] | 消息的"载荷"定义（数据结构） |

### 3.2.2 引擎实现要点

✅ Message 是 **RootElement**，在 `Definitions` 下定义，可被多个流程/事件引用。

ℹ️ **使用场景**：

- Message Start Event 触发流程
- Message Intermediate Catch/Throw Event
- Send Task / Receive Task
- Boundary Message Event
- Service Task 的输入/输出（通过 Operation）

**引擎内部模型**：

```java
interface Message {
    String getId();
    String getName();
    ItemDefinition getItemRef();  // 载荷结构
}
```

## 3.3 Error 与 Escalation

### 3.3.1 Error（错误）

> 对应原书 §8.4.3（p.109）

`Error` 表示流程执行中**抛出的业务错误**，可被 Boundary Error Event 捕获。

| 属性         | 类型           | 说明                         |
| ------------ | -------------- | ---------------------------- |
| name         | string         | 错误名称                     |
| errorCode    | string         | **错误代码**（用于匹配捕获） |
| structureRef | ItemDefinition | 错误载荷结构                 |

✅ **核心特征**：

- Error 抛出后，会**中断当前活动**，沿作用域链向上传播
- 必须由 Boundary Error Event 或 Event Sub-Process Error Start Event 捕获
- 未被捕获的 Error 会**中断整个流程实例**

### 3.3.2 Escalation（升级）

> 对应原书 §8.4.4（p.110）

`Escalation` 表示**非错误的异常情况**，用于在层级结构中向上传递控制权。

| 属性           | 类型           | 说明                         |
| -------------- | -------------- | ---------------------------- |
| name           | string         | 升级名称                     |
| escalationCode | string         | **升级代码**（用于匹配捕获） |
| structureRef   | ItemDefinition | 升级载荷结构                 |

✅ **Escalation vs Error**：

| 特性 | Error | Escalation |
| --- | --- | --- |
| 中断当前活动 | ✅ 总是 | ⚠️ 可中断可不中断（`cancelActivity` 属性） |
| 是否业务错误 | ✅ 是 | ❌ 不是错误 |
| 跨层级传播 | 沿作用域链 | 显式向父级（不中断子流程的执行） |
| 必须被捕获 | ✅ 必须捕获，否则中断流程 | ❌ 不被捕获时静默忽略 |

## 3.4 Services 包（服务定义）

> 对应原书 §8.5（p.131）

### 3.4.1 Interface（接口） ✅

`Interface` 是**一组操作的集合**，由服务实现。

| 属性 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| name | string | ✅ | 接口名称 |
| operations | Operation [1..*] | ✅ | 接口包含的操作（至少一个） |
| callableElements | CallableElement [0..*] | — | 使用此接口的可调用元素 |
| implementationRef | Element [0..1] | — | 底层实现引用（如 WSDL portType） |

### 3.4.2 Operation（操作） ✅

`Operation` 定义**调用服务时消耗和产出的消息**。

| 属性 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| name | string | ✅ | 操作名称 |
| **inMessageRef** | Message | ✅ | **输入消息**（恰好一个） |
| outMessageRef | Message [0..1] | 否 | 输出消息（最多一个） |
| errorRef | Error [0..*] | 否 | 操作可能返回的错误 |
| implementationRef | Element [0..1] | — | 底层实现引用（如 WSDL operation） |

### 3.4.3 EndPoint（端点） ℹ️

> 对应原书 §8.5.2（p.133）

`EndPoint` 是**服务地址的扩展点**。BPMN 2.0 规范**没有规定具体格式**，由其他规范（如 WS-Addressing）扩展。

引擎一般不直接消费 EndPoint，由具体的连接器/适配器负责。

## 3.5 Correlation（消息关联）

> 对应原书 §8.4.2（p.102）

### 3.5.1 为什么需要 Correlation

业务流程通常**长时间运行**（几天到几个月），且**多个实例并行**（如多个订单流程同时跑）。Correlation 用于将**异步到达的消息**关联到**正确的流程实例**。

✅ **规范性定义**：Correlation 是一组对消息（载荷）的谓词，必须全部满足才能将消息关联到特定的 Send/Receive Task。

### 3.5.2 两种关联机制

#### 机制 1：基于 Key 的关联（Key-based Correlation）

最常用、最简单的形式。

**核心元素**：

- `CorrelationKey` - 复合键（由多个 CorrelationProperty 组成）
- `CorrelationProperty` - 单个键字段（如 orderId、customerId）
- `CorrelationPropertyRetrievalExpression` - 从消息载荷提取键值的表达式

**工作流程**：

```
1. 首次发送/接收消息时，从消息载荷提取键值，初始化 CorrelationKey 实例
2. 后续消息到达时，从载荷提取键值，与已存在的 CorrelationKey 实例匹配
3. 匹配成功 → 路由到对应流程实例
4. 不匹配 → 错误或路由失败
```

✅ **规范性约束**：

- 首个消息**必须**初始化至少一个 CorrelationKey
- 后续消息若派生出已初始化的 key，则值**必须匹配**
- 后续消息若派生出未初始化的 key，则关联到该 Conversation

#### 机制 2：基于上下文的关联（Context-based Correlation）

在 Key-based 之上的增强版，允许**流程上下文动态影响匹配条件**。

**新增元素**：

- `CorrelationSubscription` - 流程级的订阅，关联到一个 CorrelationKey
- `CorrelationPropertyBinding` - 单个属性的绑定规则
  - `dataPath`: FormalExpression - 从流程上下文（Data Object、Property）提取值
  - `correlationPropertyRef`: 指向 CorrelationProperty

**工作流程**：

```
1. 流程实例启动时，初始化所有 CorrelationKey
2. 每当流程上下文（Data Object/Property）变化时，CorrelationSubscription 重新求值
3. CorrelationKey 的值随之更新
4. 后续消息匹配时使用最新的 CorrelationKey 值
```

### 3.5.3 元素属性汇总

#### CorrelationKey

| 属性                   | 类型                       | 说明                  |
| ---------------------- | -------------------------- | --------------------- |
| name                   | string [0..1]              | key 名称              |
| correlationPropertyRef | CorrelationProperty [0..*] | 组成此 key 的所有属性 |

#### CorrelationProperty

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| name | string [0..1] | 属性名称 |
| type | string [0..1] | 属性类型 |
| correlationPropertyRetrievalExpression | CorrelationPropertyRetrievalExpression [1..*] | 提取规则（每个对应一种 Message） |

#### CorrelationPropertyRetrievalExpression

| 属性        | 类型             | 说明                              |
| ----------- | ---------------- | --------------------------------- |
| messagePath | FormalExpression | **从 Message 载荷提取值的表达式** |
| messageRef  | Message          | 关联的具体 Message                |

#### CorrelationSubscription

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| correlationKeyRef | CorrelationKey | 关联的 key |
| correlationPropertyBinding | CorrelationPropertyBinding [0..*] | 各属性的绑定规则 |

#### CorrelationPropertyBinding

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| dataPath | FormalExpression | **从流程上下文提取值的表达式** |
| correlationPropertyRef | CorrelationProperty | 关联的属性 |

### 3.5.4 XML 示例

```xml
<definitions ...>
  <!-- 1. 定义 CorrelationProperty（业务字段，如订单号） -->
  <correlationProperty id="cp_orderId" name="orderId" type="xsd:string">
    <correlationPropertyRetrievalExpression messageRef="msg_placeOrder">
      <messagePath xsi:type="tFormalExpression">//order/id</messagePath>
    </correlationPropertyRetrievalExpression>
    <correlationPropertyRetrievalExpression messageRef="msg_payment">
      <messagePath xsi:type="tFormalExpression">//payment/orderId</messagePath>
    </correlationPropertyRetrievalExpression>
  </correlationProperty>

  <!-- 2. 定义 CorrelationKey（组合多个 Property） -->
  <correlationKey id="ck_orderKey" name="orderKey">
    <correlationPropertyRef>cp_orderId</correlationPropertyRef>
  </correlationKey>

  <!-- 3. 在 Receive Task 中使用 Correlation -->
  <receiveTask id="rt_waitPayment" messageRef="msg_payment">
    <correlationSubscriptions>
      <correlationSubscription correlationKeyRef="ck_orderKey" />
    </correlationSubscriptions>
  </receiveTask>
</definitions>
```

### 3.5.5 引擎实现要点

✅ **必需**：

- 维护运行时 CorrelationKey 实例的存储（通常按流程实例维度）
- 提供消息到达时的匹配机制（提取 → 比较 → 路由）
- 支持首消息初始化 key
- 支持后续消息匹配 + 衍生 key 自动填充

⚠️ **常见陷阱**：

- 多 Conversation 场景下要避免 key 冲突
- CorrelationKey 更新时要有并发控制
- 消息载荷提取失败时的处理策略（拒绝？默认值？）

ℹ️ **优化建议**：

- 用 Hash 索引 CorrelationKey 实例（按 key 值 hash）
- 引擎层提供 `CorrelationService` 抽象，与消息传输层解耦

## 3.6 引擎实践参考

### 3.6.1 服务调用的完整流程

当引擎执行一个 `ServiceTask` 时：

```
1. 解析 serviceTask.implementation（接口实现，如 ${myServiceBean}）
2. 解析 serviceTask.operationRef（要调用的 Operation）
3. 准备 inMessage 的载荷（从 dataInputAssociations 求值）
4. 调用 Operation（同步/异步）
5. 接收 outMessage 载荷
6. 通过 dataOutputAssociations 写回到流程变量
7. 若调用抛出 errorRef 中声明的 Error，触发 Boundary Error Event
```

### 3.6.2 消息接收的完整流程

当外部消息到达引擎时：

```
1. 传输层接收消息，识别消息类型（messageRef）
2. 提取所有相关的 CorrelationProperty 值（用 messagePath 表达式）
3. 在 CorrelationKey 实例库中匹配
4. 找到匹配的流程实例后，找到等待中的 Receive Task / Catch Event
5. 触发对应的 Event/Catch，将消息载荷写入流程变量
6. 推进流程执行
```

### 3.6.3 与外部系统集成的扩展点

BPMN 规范故意将以下细节**留给引擎实现**：

- 消息传输协议（HTTP/MQ/Kafka/WebSocket...）
- 服务调用机制（RPC/REST/gRPC/Messaging...）
- 错误传播机制
- 超时与重试

**引擎设计建议**：通过 SPI/Provider 模式抽象这些扩展点，让连接器以插件方式接入。
