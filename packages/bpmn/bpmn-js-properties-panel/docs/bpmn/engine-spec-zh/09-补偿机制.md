# 第 9 章 补偿机制

> 对应原规范：Ch 10.7 Compensation（p.331-334）

## 9.1 概念

**Compensation（补偿）** 是 BPMN 中**撤销已成功完成的 Activity 的结果和副作用**的机制。

✅ **核心原则**：

- 补偿只针对**已成功完成**的 Activity
- 还在运行中的 Activity **不能补偿**，只能**取消**
- 取消可能触发进一步补偿（Sub-Process 内已完成的部分）

## 9.2 Compensation Handler（补偿处理器）

> 对应原书 §10.7.1（p.332）

补偿由**补偿处理器**执行，处理器是一组**不与正常流程连接的 Activity**。

### 9.2.1 两种形式

#### 形式 1：Boundary Compensation Event + Compensation Activity

挂在 Activity 边界的 Compensation Event，触发一个**专用的 Compensation Activity**。

```
┌─────────────┐         ┌─────────────┐
│  Book Hotel │ ──(+ ⬅) │ Cancel Hotel│
└─────────────┘         └─────────────┘
   (原 Activity)          (补偿 Activity)
```

✅ **关键约束**：

- Compensation Activity 必须设 `isForCompensation=true`
- 该 Activity **只在补偿时执行**，不参与正常 flow
- 通过 Association（不是 SequenceFlow）连接到 Boundary Event

#### 形式 2：Compensation Event Sub-Process

在 Sub-Process 内部定义一个 Event Sub-Process，Start Event 是 Compensation Start Event。

```
SubProcess (Bookings)
├── Book Flight ──┐
├── Book Hotel ───┤
└── EventSubProcess (Handle Compensation)
    └── Compensation Start Event
        ├── Cancel Flight
        ├── Cancel Hotel
        └── Update Customer Record
```

✅ **关键特性**：

- 是 Sub-Process，可以包含完整逻辑
- 能访问父 Sub-Process 完成**时刻的快照数据**
- 可**递归触发**父级 Activities 的补偿

### 9.2.2 默认补偿

✅ Sub-Process 可声明 `compensable=true`，**无需显式定义 handler**：

- 引擎自动按**反向 Sequence Flow 顺序**补偿所有已完成的内部 Activity
- 每个 Activity 必须有自己的 Compensation Handler（Boundary Event 或 Compensation Event Sub-Process）

## 9.3 Compensation Triggering（补偿触发）

> 对应原书 §10.7.2（p.333）

### 9.3.1 触发源

通过 **Throw Compensation Event** 触发：

- Compensation Intermediate Event（正常流中）
- Compensation End Event

### 9.3.2 关键属性

| 属性 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| **activityRef** | Activity [0..1] | — | **指定要补偿的 Activity**（不指定时按上下文默认） |
| **waitForCompletion** | boolean | true | 是否**同步等待**补偿完成 |

### 9.3.3 触发规则 ✅

✅ **规范性要求**：

- 若指定 activityRef → 补偿该 Activity（若有 handler）
- 若不指定 → **补偿当前作用域内所有已完成的 Activities**（按反向顺序）

### 9.3.4 同步 vs 异步

| 模式 | waitForCompletion | 行为 |
| --- | --- | --- |
| **同步**（默认） | true | Throw Event 等所有 handler 完成后才继续 |
| **异步** | false | Throw Event 立即继续，handler 后台执行 |

### 9.3.5 Multi-Instance 场景的补偿 ✅

- Loop / Multi-Instance Activity 的**每个内部实例**都有自己的快照
- 触发补偿时，**对每个实例单独触发** handler
- 在当前作用域内的所有实例都会被补偿

## 9.4 Error Handling 与 Compensation 的关系

> 对应原书 §10.7.3（p.334）

### 9.4.1 Presumed Abort 原则 ✅

✅ **核心原则**：**对失败 Activity 的补偿是 no-op（无效操作）**。

含义：

- Activity 已经失败（被 Error 中断）→ 不再补偿它
- 由 Error Handler 决定如何处理已完成的 Activity（可能补偿）

### 9.4.2 默认错误处理

✅ 若 Sub-Process 抛出 Error 但**没有 Error Event Sub-Process**：

- **默认行为**：自动调用内部所有 Activity 的补偿
- 保证 auditing 和 monitoring 数据的完整

### 9.4.3 责任划分

✅ 规则：

- Error 抛出后，**Error Handler 负责善后**
- Error Handler 完成后，**不再需要补偿**
- Error Handler 内可以**显式触发补偿**（通过 Compensation Throw Event）

## 9.5 补偿的执行顺序

### 9.5.1 反向顺序原则 ✅

✅ 补偿**按 SequenceFlow 的反向顺序**执行：

- 假设正向流程：A → B → C
- 补偿顺序：C → B → A

### 9.5.2 引擎实现要点

```java
class CompensationManager {
    // 每个作用域维护"已完成 Activity 栈"
    private Deque<ActivityCompletion> completedStack;

    void onActivityCompleted(ActivityInstance activity) {
        if (hasCompensationHandler(activity)) {
            completedStack.push(new ActivityCompletion(activity, snapshotData));
        }
    }

    void compensate(ScopeInstance scope, Activity target) {
        if (target != null) {
            // 补偿特定 Activity
            compensateSingle(target);
        } else {
            // 反向补偿所有
            while (!completedStack.isEmpty()) {
                ActivityCompletion c = completedStack.pop();
                compensateSingle(c);
            }
        }
    }

    private void compensateSingle(ActivityCompletion c) {
        CompensationHandler handler = findHandler(c.getActivity());
        if (handler != null) {
            handler.executeWithSnapshot(c.getSnapshotData());
        }
    }
}
```

### 9.5.3 快照数据 ✅

✅ Activity 完成时，引擎需要**保存当时的流程变量快照**，供补偿 handler 使用。

- Loop Activity：每次迭代完成都保存一份
- Multi-Instance：每个内部实例的快照独立保存
- Sub-Process：保存子流程完成时刻的完整变量

## 9.6 与 Transaction 的协作

Transaction Sub-Process 的 Cancel 结果会：

1. 取消所有运行中的内部 Activity
2. 触发**反向补偿**所有已完成的内部 Activity
3. 通过 Cancel Boundary Event 离开

## 9.7 引擎实现清单

### 9.7.1 必需能力

✅ **必须实现**：

- 维护每个 Activity 的完成历史（用于反向补偿）
- 保存完成时的变量快照
- 识别并调用 Compensation Handler
- 反向顺序执行

### 9.7.2 性能考虑

- 快照数据可能占用大量内存（特别是 Loop/Multi-Instance）
- 建议用增量快照（只记 diff）或持久化存储
- 提供**过期补偿记录清理**机制

### 9.7.3 常见陷阱

| 陷阱                        | 说明                         |
| --------------------------- | ---------------------------- |
| 补偿未完成的 Activity       | 应跳过（presumed abort）     |
| 补偿 handler 内部抛异常     | 引擎应记录但继续后续补偿     |
| Loop 每次迭代都需要快照     | 否则只能补偿最后一次的状态   |
| 嵌套 Sub-Process 的补偿顺序 | 由内向外、反向顺序           |
| 补偿 handler 自身失败       | 通常不补偿补偿，需要人工介入 |

## 9.8 实践建议

1. **能不用补偿就不用**：补偿设计复杂、容易出错，能通过其他机制（如 Saga）解决就别用 BPMN Compensation
2. **Transaction Sub-Process 与 Compensation 联用**：Transaction 提供框架，Compensation 处理细节
3. **明确补偿边界**：补偿 handler 应**幂等**，可能被多次调用
4. **快照数据要精简**：只保存反向恢复必需的字段，避免存储成本爆炸
