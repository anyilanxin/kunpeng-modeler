# 第 11 章 执行语义

> 对应原规范：Ch 13 BPMN Execution Semantics（p.455-473）⭐ 引擎开发的核心章节

## 11.1 概述

> 对应原书 §13.1（p.455）

✅ **本章对 Process Execution Conformance 是强制必需的**。

执行语义通过 **token**（令牌）这一概念描述：token 是抽象的"执行控制点"，沿着 SequenceFlow 流动，触发经过的元素行为。

⚠️ **重要说明**：token 是**理论概念**，引擎实现**不强制**采用 token 模型。

### 11.1.1 非操作性元素（Non-operational）

✅ 以下元素引擎**可以忽略**，不需实现执行语义：

- Manual Task / Abstract Task
- DataState
- IORules
- Ad-Hoc Process
- ItemKind=Physical 的 ItemDefinition
- DataInput 的 inputSetWithWhileExecuting
- DataOutput 的 outputSetWithWhileExecuting
- Process 的 isClosed
- SequenceFlow 的 isImmediate

## 11.2 流程实例化与终止

> 对应原书 §13.2（p.456）

### 11.2.1 实例化触发 ✅

✅ **规范性要求**：以下三种情况会创建新的 Process Instance：

1. **Start Event 触发**：每个 Start Event 触发都创建新实例（除非参与 Conversation，按 Correlation 合并）
2. **Event-Based Gateway（instantiate=true）**：第一个事件触发即创建
3. **Receive Task（instantiate=true，无入向 SequenceFlow）**：消息到达即创建

### 11.2.2 关键约束 ✅

✅ **规范性要求**：

- 全局 Process **不能**有空 Start Event、无入向的 Gateway 或 Activity（Event Gateway 例外）
- 多个 Start Event 是**替代关系**（alternative），一个触发不等待其他
- 每个 Start Event 触发都为出向 SequenceFlow 创建 token

### 11.2.3 实例完成条件 ✅

✅ Process Instance 完成**必须同时满足**：

1. 若实例化是通过 Parallel Event Gateway，则**所有后续 Events 都已触发**
2. **没有 token 残留**
3. **没有 Activity 处于 ACTIVE 状态**

✅ token 到达 End Event 时：

- 触发 End Event 类型对应的行为（Message 发送、Signal 广播等）
- 消耗 token
- Terminate End Event 会**异常终止整个 Process**

## 11.3 活动（Activity）执行语义

> 对应原书 §13.3（p.457-463）

### 11.3.1 Sequence Flow 考虑 ✅

✅ **非受控流（Uncontrolled Flow）**：Activity 有多个入向 SequenceFlow 时，**任一 token 到达即触发**，相当于**隐式 Exclusive Gateway**（不同步）。

✅ **多出向 SequenceFlow 行为**：

- 全无条件 → **隐式 Parallel Gateway**（并行分叉）
- 全有条件 → **隐式 Inclusive Gateway**（包容分叉）
- 混合（部分有条件） → **Parallel + Inclusive 组合**

✅ **isImmediate 语义**：

- true：token 在 SequenceFlow 上移动时，**不允许**执行其他非模型内 Activity
- false：允许

### 11.3.2 Activity 生命周期 ⭐

```
                  (足够 token 到达)
                          ↓
                  ┌─────────────┐
                  │    READY    │ ← 等待 InputSet
                  └──────┬──────┘
                         │ InputSet available
                         ↓
                  ┌─────────────┐
        ┌────────│   ACTIVE    │ ← 执行中
        │        └──────┬─────┘
        │               │
        │   ┌───────────┼───────────┐
        │   │           │           │
        │  fail      interrupt    complete
        │   │           │           │
        │   ↓           ↓           ↓
        │  FAILED   TERMINATING  COMPLETING
        │              ↓           │
        │           (interrupted   │ 所有 handler 完成
        │            by event)     ↓
        │                        COMPLETED
        │                            │
        │                            │ 补偿触发
        │                            ↓
        │                       COMPENSATING
        │                            │
        │                            ↓
        │                       COMPENSATED
        │                       (or FAILED/TERMINATED)
```

✅ **关键状态说明**：

| 状态 | 触发条件 | 行为 |
| --- | --- | --- |
| **READY** | 必需 token 数到达（startQuantity） | 等待 InputSet 可用 |
| **ACTIVE** | 某个 InputSet 满足 | 执行 Activity |
| **COMPLETING** | Activity 执行结束，等待 Event Handler 完成 | 中间态，不再创建新 Event Handler |
| **COMPLETED** | 所有完成依赖满足 | 产出 token 到出向流 |
| **FAILED** | Activity 内部失败 | 等待错误处理 |
| **FAILING** | 被中断型 Error 触发 | 等待 Error Handler 处理 |
| **TERMINATING** | 被其他中断型事件触发 | 等待 Handler 处理 |
| **TERMINATED** | 终止完成 | 终态 |
| **COMPENSATING** | 补偿被触发 | 执行补偿 |
| **COMPENSATED** | 补偿完成 | 终态 |

### 11.3.3 InputSet 选择算法 ✅

✅ Activity 从 READY 到 ACTIVE 的条件：

```
for each InputSet (按顺序):
    评估每个 DataInput 是否可用（从 DataAssociation 求值）
    if 所有必需的 DataInput 都可用:
        使用此 InputSet 启动 Activity
        return
继续等待
```

### 11.3.4 OutputSet 选择算法 ✅

✅ Activity 完成时的 OutputSet 选择：

```
for each OutputSet (按顺序):
    if 所有必需的 DataOutput 都有值:
        通过 DataAssociation 推送到上下文
        return
throw runtime exception（无可用 OutputSet）
```

### 11.3.5 各 Task 类型的执行语义 ✅

| Task | 激活时 | 完成时 |
| --- | --- | --- |
| **ServiceTask** | 从 DataInput 写入 inMessage → 调用 Operation | 从 outMessage 写入 DataOutput；服务故障 → 视为 Error |
| **SendTask** | 从 DataInput 写入 Message → 发送 | 立即完成 |
| **ReceiveTask** | 注册消息订阅 | 消息到达 → 写入 DataOutput |
| **UserTask** | 分配给用户/组 | 用户标记完成 |
| **ManualTask** | （概念模型，引擎不执行） | — |
| **BusinessRuleTask** | 调用规则引擎 | 规则引擎完成 |
| **ScriptTask** | 执行脚本 | 脚本完成 |
| **AbstractTask** | （概念模型） | — |

### 11.3.6 Sub-Process 实例化 ✅

✅ **规范性要求**：

- Sub-Process 被 token 到达时**实例化**
- Sub-Process 可以有：
  - 唯一的 None Start Event（实例化时获得 token）
  - 或没有 Start Event，但有无入向的 Activity / Gateway（都获得 token）
- Sub-Process **不能**有非 None 的 Start Event
- Sub-Process Instance 完成条件：**没有 token 残留**且**没有内部 Activity 仍在 ACTIVE**

### 11.3.7 Call Activity ✅

✅ **行为与 Sub-Process 相同**，但被调用的全局 Process 可以有非 None Start Event（**这些非 None Start Event 被忽略**）。

### 11.3.8 Ad-Hoc Sub-Process ✅

✅ **执行算法**：

1. 初始：所有无入向的 Activity 都被 enabled
2. 由 Human Performer 选择执行哪个 enabled Activity
3. ordering=Sequential：上一个完成才能选下一个
4. ordering=Parallel：随时可选新的
5. 每次完成内部 Activity 后，评估 completionCondition：
   - false：刷新 enabled 集合
   - true：完成整个 Ad-Hoc Sub-Process
6. Parallel 模式 + cancelRemainingInstances=true：取消所有运行中实例

### 11.3.9 Loop Activity ✅

```
testBefore=true:
  while (loopCondition && iterations < loopMaximum):
    execute Activity
    iterations++

testBefore=false:
  do:
    execute Activity
    iterations++
  while (loopCondition && iterations < loopMaximum)
```

支持工作流模式：**WCP-21 Structured Loop**。

### 11.3.10 Multi-Instance Activity ✅

✅ **执行步骤**：

1. **确定实例数**：求值 loopCardinality 或 loopDataInputRef 的集合大小
2. **创建实例**：
   - isSequential=true：串行，一个完成才创建下一个
   - isSequential=false：并行，一次性创建所有
3. **数据分配**：从 loopDataInput 取第 i 个元素 → inputDataItem
4. **执行每个内部实例**
5. **完成处理**：
   - 每个实例完成时，将 outputDataItem 写入 loopDataOutput 对应位置
   - 每次完成都评估 completionCondition：true → 取消剩余实例，完成 MI
6. **behavior 属性控制 token 产生**：
   - all（默认）：所有实例完成才产生 token
   - one：第一个完成时抛出事件
   - none：每个完成都抛出事件
   - complex：自定义

支持工作流模式：**WCP-21, WCP-13/14/34/36 Multiple Instance Patterns**。

## 11.4 Gateway 执行语义

> 对应原书 §13.4（p.464-468）

### 11.4.1 Parallel Gateway（AND）

✅ **激活条件**：每个入向 SequenceFlow 都至少有一个 token。

✅ **行为**：

- 从每个入向流消耗**一个** token
- 为每条出向流产生**一个** token

✅ **多余 token**：若某入向流有多个 token，**剩余的保留**在原位。

### 11.4.2 Exclusive Gateway（XOR）

✅ **激活条件**：任一入向流有 token 即激活。

✅ **行为**：

- 从到达的入向流消耗一个 token
- 按**顺序**评估出向流的条件
- 第一个为 true 的条件决定走哪条
- 都不满足 → 走 default 流
- 都不满足且无 default → **抛出异常**

支持工作流模式：**WCP-4 Exclusive Choice, WCP-5 Simple Merge, WCP-8 Multi-Merge**。

### 11.4.3 Inclusive Gateway（OR）

✅ **激活条件**（**复杂**）：

- 至少一个入向流有 token
- 对于每个"有 token 的路径 → 无 token 的入向流"的路径集合，存在"无 token 入向流 → 有 token 入向流"的反向路径（即上游未激活的入向流才需要等待）

✅ **行为**：

- 从每个有 token 的入向流消耗一个
- **评估所有出向流条件**（任意顺序）
- 所有 true 的出向流都获得 token
- 都不满足 → default 流
- 都不满足且无 default → 异常

支持工作流模式：**WCP-6 Multi-Choice, WCP-7/37/38 Synchronizing Merge**。

### 11.4.4 Event-Based Gateway

✅ **激活条件**：任一入向流有 token 即激活。

✅ **行为**：

- 为每个出向流的目标 Event / Receive Task 创建订阅
- **第一个触发的事件胜出**
- 其他订阅立即取消
- token 走向胜出事件的出向流

支持工作流模式：**WCP-16 Deferred Choice**。

### 11.4.5 Complex Gateway

✅ **激活条件**：求值 `activationExpression` 为 true。

✅ **两阶段状态**：

- **waitingForStart**（初始）：等待 activationExpression 为 true
- **waitingForReset**：激活后等待剩余 token

⚠️ **风险**：activationCondition 永远不为 true 会导致死锁。

支持工作流模式：**WCP-9, WCP-28, WCP-30, WCP-31 Discriminator / Partial Join**。

## 11.5 事件执行语义

> 对应原书 §13.5（p.469-473）

### 11.5.1 Start Event

✅ **行为**：每次触发创建新的 Process Instance（除非参与 Conversation，按 Correlation 合并）。

### 11.5.2 Intermediate Event（正常流中）

✅ **Catch**：到达时开始等待，触发后 token 继续。✅ **Throw**：到达时立即抛出，token 继续。

### 11.5.3 Boundary Event

✅ **处理流程**：

1. 宿主 Activity 进入 ACTIVE 时，订阅激活
2. 触发器到来时：
   - `cancelActivity=true`：**取消**宿主 Activity（包括其内部所有多实例）
   - `cancelActivity=false`：宿主继续，产生**新的并行 token**
3. token 从 Boundary Event 的出向流离开

### 11.5.4 Event Sub-Process

✅ **核心特点**：

- 不连接到正常 SequenceFlow
- 由 Start Event 触发实例化
- 运行在父 Sub-Process / Process 的**作用域内**

✅ **interrupting=true**：

- 取消父 Activity 执行
- 父 Activity 进入 Failing（Error 触发）或 Terminating（其他事件）

✅ **interrupting=false**：

- 父 Activity 继续执行
- Event Sub-Process 并行运行
- 可多次触发，产生多个并行实例

✅ **父 Activity 完成时**：

- 若在 COMPLETING 状态，等待所有 active Event Sub-Process 完成
- 不再启动新的 Event Sub-Process

### 11.5.5 Compensation 详细执行 ⭐

#### Compensating Activity 的启用 ✅

- 父 Activity 进入 COMPLETED 状态时
- 拍摄**数据快照**（Data Snapshot）
- Compensation Event Sub-Process 进入"已启用"状态
- 多实例 / 循环 Activity：**每个实例单独**保存快照

#### Compensation 触发 ✅

- Compensation Event Sub-Process 激活时，**恢复快照数据**
- 多实例 Activity：为**每个实例**激活独立的 Compensation Handler
- Boundary Compensation Activity：只**触发一次**（需要补偿所有实例）

#### 反向顺序补偿 ✅

✅ 默认补偿**逆序执行**，依赖关系：

| 关系                                            | 反向规则         |
| ----------------------------------------------- | ---------------- |
| A → B（SequenceFlow）                           | B 补偿先于 A     |
| A → B（数据依赖）                               | B 补偿先于 A     |
| Ad-Hoc 中 A 先 B 完成时                         | B 补偿先于 A     |
| 循环 / 串行多实例                               | 逆序补偿         |
| 并行多实例                                      | **可以并行补偿** |
| Sub-Process A 有 Boundary Event 触发 Activity B | B 补偿先于 A     |

#### Presumed Abort 原则 ✅

✅ 失败的 Activity 不补偿（补偿失败 Activity 是 no-op）。✅ 无 Error Handler 时，Sub-Process 出错会**自动触发**所有内部 Activity 的补偿。

### 11.5.6 End Event 语义

#### Process 级 End Event

| 类型          | 行为                                                      |
| ------------- | --------------------------------------------------------- |
| **Terminate** | Process 异常终止；**其他正在进行的 Process 实例不受影响** |
| 其他          | 执行 End Event 类型对应行为（发 Message/Signal 等）       |

✅ Process 完成的额外条件：

- 所有 Start Node 都已访问（所有 Start Event 已触发，所有 starting Event-Based Gateway 至少一个事件触发）
- 没有 token 残留

#### Sub-Process 级 End Event

| 类型 | 行为 |
| --- | --- |
| **Terminate** | 仅终止**当前 Sub-Process**；其他实例和父流程不受影响 |
| **Cancel** | 终止 Sub-Process + 关联 Transaction 回滚，通过 Cancel Boundary Event 离开 |
| 其他 | 执行对应行为 |

## 11.6 引擎实现要点（综合）

### 11.6.1 Token 模型

引擎可以选择是否使用 token 模型。常见实现方式：

**方式 1：Token 队列**

- 每个流程实例维护 token 队列
- token 包含位置（当前节点）、变量上下文、parent 等

**方式 2：Execution Tree**

- 用执行树表示 token 层次结构
- 每个 Execution 对应一个 token，可派生子 Execution

**方式 3：Event Sourcing**

- 每个状态变化都是事件
- 状态通过事件回放得到（kunpeng 项目采用的方式）

### 11.6.2 状态机驱动

引擎核心是**Activity 状态机**：

```java
enum ActivityState {
    READY, ACTIVE, COMPLETING, COMPLETED,
    FAILED, FAILING, TERMINATING, TERMINATED,
    COMPENSATING, COMPENSATED
}

void transition(ActivityInstance instance, ActivityState newState) {
    validateTransition(instance.getState(), newState);
    instance.setState(newState);
    eventBus.fire(new ActivityStateEvent(instance, newState));
    onStateChanged(instance, newState);
}
```

### 11.6.3 并发控制

Activity 实例的状态变化需要**线程安全**：

```java
class ActivityInstance {
    private final Lock stateLock = new ReentrantLock();

    void transition(ActivityState newState) {
        stateLock.lock();
        try {
            // 状态机转换逻辑
        } finally {
            stateLock.unlock();
        }
    }
}
```

或采用 **Actor 模型**（kunpeng 项目的 scheduler 模块）：每个 Activity Instance 由独立 Actor 处理，天然串行。

### 11.6.4 死锁检测

⚠️ 引擎应提供死锁检测机制：

- 长时间停留在某个状态的 Activity
- 等待永远不会到达的 token 的 Gateway
- 等待 Event 但 Event 永远不触发的 Catch Event

### 11.6.5 持久化策略

为支持长时间运行，引擎需要持久化：

- Process Instance 状态
- Activity Instance 状态机
- Variable 数据
- Event Subscription
- Job（Timer、异步任务）
- Compensation Snapshot
